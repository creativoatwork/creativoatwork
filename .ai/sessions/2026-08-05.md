# Session 2 — Contact endpoint rate limiting

## Objective

Close the backlog's top item: no rate limiting on the public contact endpoint.

## Design path

Brainstormed to a layered design (3/min burst + 10/hour KV cap + invisible Turnstile), then the operator constrained scope to "free, no added headaches, no complexity at all." Rescoped to the native Cloudflare rate-limiting binding alone. Full reasoning and accepted trade-offs are in `decisions.md`.

Worth noting for future work: DNS for `creativoatwork.com` is on Porkbun with an A record to Firebase Hosting (`199.36.158.100`). The domain is **not** proxied through Cloudflare, so zone-level WAF rate limiting rules are unavailable — enforcement has to live in the Worker. The Cache API is also a dead end here: it is a no-op on `workers.dev` subdomains.

## Changes

- `worker/wrangler.toml` — `CONTACT_RATE_LIMITER` ratelimit binding, 3 per 60s.
- `worker/src/index.ts` — `RateLimiter` type, `RATE_LIMIT_PERIOD_SECONDS`, and a fail-open limit check placed after honeypot and validation.
- `src/components/Contact.tsx` — `rate_limited` copy in `ERROR_COPY`.

## Verification — actually run

- `worker: npm run typecheck` → clean.
- `npm run build` (frontend) → clean, built in 407ms.
- `wrangler dev` + curl against `localhost:8787`:
  - 5 rapid posts from one IP → **502, 502, 502, 429, 429**. The 502s are expected: no `RESEND_API_KEY` locally, so Resend 401s and the worker maps it to `send_failed`. Three got through, the fourth was limited.
  - A different `CF-Connecting-IP` → 502, i.e. not limited. Per-IP keying confirmed.
  - 429 response carries `Retry-After: 60`, the correct CORS origin, and `{"ok":false,"error":"rate_limited"}`.
- The limiter bound as `[connected to remote resource]` in local dev, so this exercised real enforcement rather than a stub.

**Not verified:** behavior on the deployed worker (not deployed this session), and the browser-side rendering of the `rate_limited` message.

- `npm audit` reports issues in worker dev dependencies. Not investigated.
